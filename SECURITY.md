# Fourth Step privacy and security

Status: the implementation is public and has automated regression checks. **No independent security audit has been completed.** Please do not describe it as audited, unconditionally anonymous, or immune to a malicious website update.

## What the current release does

The app has no answer API, inventory database, account system, analytics, or inventory administration screen. All inventory content (timestamped check-ins, sessions, in-progress drafts, settings, support contacts, and migrated legacy data) is encrypted on the user's device before it is persisted. Unlock secrets are entered or derived locally and are never stored in readable form or transmitted. Website hosting still sees ordinary request metadata when the app is downloaded.

### Key hierarchy (vault format 2)

```
data key: random AES-256-GCM, generated on the device, never stored unwrapped
 ├─ recovery slot  PBKDF2-HMAC-SHA-256 (600,000 iterations, 128-bit salt) of the recovery key or passphrase   · vault + backups
 ├─ passkey slots  HKDF-SHA-256 of a WebAuthn PRF output (32-byte random PRF salt per slot)                   · vault + backups
 └─ PIN record     PBKDF2-HMAC-SHA-256 (600,000 iterations) of a 6–12 digit PIN, 5 attempts                    · this browser only
```

Each slot wraps the data key with AES-GCM using a fresh 96-bit nonce; the slot's additional data binds it to the vault ID, slot kind, and credential ID, so a wrapped key cannot be moved between vaults or slots. The envelope in `fourthstep_vault_v1` contains format/version, a random vault ID, the slots, a cipher block (`AES-GCM`, nonce, `gzip` or `json` encoding), and the ciphertext. The entire header, including every slot, is canonically serialised and authenticated as additional data on the inventory ciphertext, so adding, removing, or editing any slot is detected. Plaintext is gzip-compressed (CompressionStream) before encryption to extend storage capacity for the check-in time series. Parameters are strictly validated before any derivation, with a 32 MB limit. Non-extractable keys are used for normal operation; an extractable copy of the data key exists only transiently, inside the call that wraps it for a newly added unlock method.

Format 1 vaults (the passphrase-derived key encrypted data directly) still open. On unlock they are re-keyed under a new random data key with a recovery slot for the same passphrase, data is upgraded to the current schema (earlier HALT check-ins become timeline entries), and the first save replaces the stored copy using the same compare-before-write rule as every other save. Format 1 backups also restore.

Sources: [Web Crypto wrapKey](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/wrapKey), [AES-GCM nonce requirements](https://developer.mozilla.org/en-US/docs/Web/API/AesGcmParams), [OWASP cryptographic storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html), [OWASP PBKDF2 work factor](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [WebAuthn PRF extension](https://w3c.github.io/webauthn/#prf-extension).

## Unlock methods and their trade-offs

**Recovery key (always present).** By default the app generates 100 random bits shown as five groups of Crockford base32 (`XXXX-XXXX-XXXX-XXXX-XXXX`); input is normalised for case, spacing, and commonly confused characters. Users may instead choose a passphrase of at least 12 characters (NFC-normalised; obvious patterns rejected). Length alone does not ensure entropy, which is why the generated key is the default. Setup requires typing the last group back to confirm it was saved. While unlocked, the recovery secret can be replaced after re-verification with any current unlock method; this rewraps only the data key. Older backups keep the slot that was current when they were made.

**Device unlock (passkey + PRF).** `navigator.credentials.create/get` with `userVerification: 'required'`, a platform authenticator, no attestation, a random user handle, and the discreet account name "Private vault". The PRF output (CTAP2 `hmac-secret`) is only released after the device verifies the user (biometric or device screen lock), and the authenticator or passkey provider enforces attempt limits. It is HKDF-expanded into a wrapping key; it is never stored or transmitted. The challenge is random and nothing is verified server-side because no sign-in takes place: possession of the PRF output is the security property. Passkeys are bound to the website's hostname (`rpId`), so they do not work in the offline file or on a different domain. Synced passkeys (iCloud Keychain, Google Password Manager) carry the same PRF secret to the user's other devices, so a restored backup can open with device unlock there. A passkey whose platform reports no PRF support is discarded and reported to the password manager with the Signal API where supported. Removing a device also signals its credential as unknown. Support (October 2026): Safari 18+ on iOS/iPadOS/macOS, Chrome/Edge with Google Password Manager or iCloud Keychain, Windows Hello since the February 2026 Windows 11 update; Firefox support varies.

**PIN (optional, this browser only).** A 6–12 digit PIN wraps the data key in a separate record (`fourthstep_pin_v1`) that is never part of the vault envelope or any backup. Five consecutive wrong PINs delete the record; a correct PIN resets the count. Repeated and sequential PINs are rejected. **Honest limit:** the attempt counter is enforced by the app, not hardware. An attacker who copies the browser profile can run an offline search: a 6-digit PIN at 600,000 PBKDF2 iterations falls to a single modern GPU in minutes. The PIN therefore protects against casual access to an unlocked or nearby device, not against forensic extraction. The UI states this when the PIN is offered; device unlock is presented first where available.

## Storage, migration, and recovery

The vault module owns active persistence. Plaintext storage functions remain in the earlier code for migration compatibility and existing domain tests; the live inventory screens cannot call them. Session writes are queued, and every update (including slot changes) merges against the latest in-memory state. Expected ciphertext is compared before a write. Web Locks serialize cooperating tabs where supported; the comparison is a best-effort conflict guard on browsers without Web Locks, not a universal cross-process transaction.

Migration from readable storage validates old sessions, makes an encrypted archive of all original inventory keys (including older HALT logs and tasks), backfills timeline check-ins from earlier HALT logs and answered sessions, encrypts and decrypts a copy, writes it, verifies the stored copy, and only then removes exact matching originals. It never clears unrelated storage. Corrupt/future-version data blocks replacement. If another tab changes an original, that original is kept and the UI reports incomplete cleanup. Browser storage deletion is not secure physical erasure: device backups, browser sync/history, disk recovery, or copies already made may still contain previous readable records.

A failed save keeps the last stored ciphertext and retains the latest changes in memory. The UI warns, protects against accidental page closure while saving, and offers an encrypted recovery backup. Another-tab conflicts do not overwrite its ciphertext. A backup encrypts the current memory snapshot, including unsaved edits, with the current recovery and passkey slots. Restore verifies decryption before writing and is allowed only when no inventory already exists in the destination. There is no automatic merge of backups and no server-side reset.

Lock saves first, then unmounts inventory screens and drops the module's key and data references. The app locks after 15 minutes without interaction and, when the page returns from the background, if it was hidden longer than the user's chosen limit (1, 5, or 15 minutes). The workspace is covered as soon as the page is hidden, so app-switcher snapshots are less likely to show answers. Suspended browsers may delay timers until execution resumes. **If saving fails, automatic or manual locking leaves the page open to protect unsaved work and shows a recovery warning.** JavaScript cannot guarantee physical memory zeroization. An attacker with process access remains out of scope.

## Exports

Readable exports are explicit user actions and are labelled as outside the vault: printed reviews, text downloads, the device share sheet, a formatted copy for pasting into Google Docs, and a CSV of check-ins. The app does not connect to Google: the user pastes into a document they open themselves (`docs.new` is an ordinary link). Signing in with Google was considered and rejected: it would require loading Google's script into the page that holds decrypted answers, opening `connect-src` to Google APIs, and it would still store plaintext with Google. The HTML copy escapes all answer text. CSV cells beginning with `=`, `+`, `-`, `@`, tab, or carriage return are prefixed with `'` to prevent formula execution in spreadsheet software ([OWASP CSV injection](https://owasp.org/www-community/attacks/CSV_Injection)).

## Website updates and offline edition

A website owner or compromised deployment pipeline could ship code that captures secrets or decrypted answers on a future visit. Browser encryption cannot eliminate this trust boundary. The production CSP blocks `fetch`, XHR, WebSocket, and beacon connections (`connect-src 'none'`), service workers (`worker-src 'none'`), framing, forms, and plugins. Permissions-Policy disables camera, microphone, geolocation, payment, USB, serial, HID, display capture, and Topics, and allows WebAuthn and clipboard writes only for the site itself. COOP/CORP isolate the browsing context. Inline Next.js bootstrap scripts are still permitted (`'unsafe-inline'`). These headers are defense in depth, not proof against malicious first-party code. The web app manifest makes the site installable but deliberately has no service worker: every launch loads the current release, exactly like the website, so installation does not change the trust model.

The offline edition bundles the same vault and UI in a single HTML file. It has no auto-update mechanism, external assets, or module imports. Its embedded CSP denies connections and uses an exact SHA-256 hash to authorize the one bundled script. Device unlock is unavailable there (WebAuthn requires a web origin); the recovery key and PIN work. The published SHA-256 checksum and source-revision file identify release content; because they are distributed by the same owner, they are not independent attestations. Self-contained does not mean audited.

## Threat model

Protected: passive reading of the app's browser storage or encrypted backups without an unlock secret; offline guessing against the generated recovery key or device passkeys; moving key slots between vaults; ciphertext/header/slot tampering; accidental plaintext persistence of new inventory content; routine failed saves; cooperating stale-tab writes; accidental loss during migration; casual access by someone who picks up a locked device.

Not protected: weak chosen passphrases; offline guessing of a PIN by someone who has copied the browser profile; compromised website releases; hostile extensions, malware, browser/OS compromise; an unlocked screen; memory inspection; screenshots; a compromised Apple/Google account that syncs passkeys; printed, pasted, shared, or exported readable copies; backups already made from the old plaintext release. Nobody should put answers in URLs, error reports, issue attachments, console logs, or analytics.

## Evidence and independent review handoff

Run `pnpm typecheck`, `pnpm test`, `pnpm build`, and `pnpm test:privacy`. CI repeats these on pushes and PRs. Unit checks use real Node Web Crypto with fixture data. They cover wrong secrets, authenticated header, slot, and ciphertext tampering, injected slots, unique nonces, queued updates, failed writes and recovery, format 1 vaults and backups, generated-key normalisation, passkey PRF unlock (simulated PRF outputs), passkey removal, recovery replacement, PIN attempts and lockout, PIN exclusion from backups, complete migration archives, malformed/future data preservation, conflicting tabs, restore refusal into an occupied browser, timeline backfill, time-zone handling, insight thresholds, HTML escaping, and CSV formula neutralisation. Source/offline checks verify the persistence boundary, known egress APIs, absence of answer API routes, required headers, PRF/user-verification settings, PIN exclusion from backups, the offline script/CSP hash, syntax, checksum, and external assets. **Static API checks are limited and are not a browser runtime network audit.** Dependency vulnerabilities and arbitrary future code are not proven absent by these checks.

An independent reviewer should:

- Review `lib/inventory-vault.ts` against the properties above: key wrapping and AAD binding, canonical header serialisation, nonce uniqueness, KDF validation, transient extractability, PIN record handling, format 1 upgrade, cleanup failures, and conflict handling.
- Review `lib/device-unlock.ts`: RP ID binding, user verification, PRF salt handling, behaviour when PRF is unsupported, and Signal API use. Test on real iOS, Android, macOS, and Windows authenticators.
- Inspect the entire emitted JavaScript and offline HTML for egress paths, logging, remote assets, and code not covered by the source pattern checks.
- Use only synthetic inventories while recording browser network traffic through create, each unlock method, check-ins, each guided step, reload, edit, complete, contacts, exports, backup, restore, lock, background lock, and idle timeout.
- Confirm that no synthetic answers or secrets leave the browser, including via paths, query strings, forms, image requests, error reporting, and unexpected dependencies.
- Exercise storage denial/quota, older/corrupt versions, tab races, suspended timers, browser restart, private browsing, and supported local-file browsers. Confirm users can recover unsaved edits and no existing data is silently overwritten.
- Publish reviewer identity, exact commit/file checksum, scope, findings, fixes, and date before updating the audit status.

Report suspected issues privately to the repository owner via their GitHub profile. Never include real inventory answers or secrets in a report. A dedicated private vulnerability-reporting channel should be established before claiming a formal disclosure program.
